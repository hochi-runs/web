## Contact operator procedure (unexecuted)

1. Label owner confirms the private recipient and approves a separate public fallback destination, if desired. Hosting operator supplies `RESEND_API_KEY`, `CONTACT_FROM_EMAIL`, and `CONTACT_TO_EMAIL` as server-only settings. Do not copy them into client variables, repository, commands, screenshots, or logs. Sender must use a domain approved and verified with Resend; see [Resend verified domains](https://resend.com/docs/dashboard/domains/introduction).
2. Confirm the authorized deployment exposes an enabled Contact form. Validate existing provider/domain settings and hosting abuse controls. Check that the hosting edge preserves the visitor Host and sets a single correct `x-forwarded-proto`; the contact check deliberately ignores `x-forwarded-host`. Browser Host is a forbidden script-set header ([MDN Host reference](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Host)); that does not prevent direct scripted abuse. Syntax-valid environment settings do not prove a verified sender or deliverability.
3. Obtain permission for one benign test inquiry to the approved recipient. Fill the visitor form with approved test details. Record pending UI, final UI, timestamp and HTTP status; preserve the submitted text locally if submission cannot be confirmed. No unapproved inquiry recipient is substituted.
4. Record the provider's accepted message ID and status privately using its dashboard. The implemented REST payload uses the fixed recipient, verified sender, visitor `reply_to`, subject and plain `text`; it expects a nonempty response `id`. Confirm against [Resend send-email contract](https://resend.com/docs/api-reference/emails/send-email).
5. Recipient independently confirms inbox receipt and reply destination, including spam-folder checks if absent. Record “provider accepted” and “recipient confirmed receipt” separately. An accepted HTTP response is not receipt evidence. A timeout can have occurred after acceptance; investigate provider logs before repeating the same inquiry.
6. On staging, simulate missing configuration/provider rejection and test pending/error/input retention, invalid input, unsupported/cross-origin requests and keyboard announcements. Do not deliberately break production credentials. Check narrow layout and JavaScript-disabled availability. Then capture the actual deployed contact result.
7. Recovery: correct provider/domain/routing settings and redeploy using existing procedures; until validated, keep availability truthful. Publish only an owner-approved fallback address. Remove/disable delivery settings to restore the existing unavailable state if rollback is needed.

## Editor publishing procedure (unexecuted)

Mode choice must be explicit. Both URL settings empty select local content. `WORDPRESS_ARTISTS_URL` plus managed artist slugs selects artist-only mode, keeping local non-artist collections. `WORDPRESS_CONTENT_URL` selects full bridge: required published collections, optional page/appearance/release overrides. Do not enable both. Local-demo HTTP allowances are explicitly rejected in production.

1. Administrator verifies the chosen canonical public content endpoint, installed plugin/version and server settings in the intended deployment. Keep connection secrets private. In full bridge, inspect/setup existing entries before importing: import skips existing records, including drafts/trash; updating a ZIP does not overwrite owner content. See [plugin guide](../../wordpress/hochi-content/README.md).
2. Editor chooses one existing artist and owner-approved reversible biography edit. Record its stable route and current text. Save as Draft first on an authorized test record; verify draft/private/password-protected material is absent from the public JSON and visitor page. Do not unpublish a live owner entry solely for testing.
3. Publish/update the approved content and record save time. Read the public feed anonymously, checking only expected published fields. Verify route name remains stable and saved release selections stay intact. Full bridge: also check empty list semantics and an approved override without changing Bandcamp source metadata.
4. Without notification, request the visitor page after its cached content is older than 60 seconds, then request again after background regeneration. Record first observation and fresh observation separately; do not promise every edit appears within exactly 60 seconds.
5. With notification enabled, inspect WordPress **Connection** result after save. A successful POST expires tagged CMS data; it does not prove a visitor already loaded new content. Request a visitor page and record actual freshness time. Existing tabs/client caches may need navigation or reload.
6. Verify `POST /api/wordpress/revalidate` with no/incorrect Authorization returns 401 (503 if no valid server secret); authorized but disconnected CMS returns 409. Only the exact bearer header is accepted. Do not put a real secret in a URL or captured shell command. Verify configured notification can invalidate only the fixed CMS tag/routes.
7. In staging, simulate upstream failure after a successful page, checking last successful ISR output, visible run/error evidence, and subsequent recovery. Separately exercise cold-render/build failure; there is no guarantee of a cached page on first request. Do not claim an active CMS outage falls back to seed content.
8. Restore the approved test edit through the editor and verify the same publication path. Record host/environment, plugin version, source revision, save/publish times, observed page time, anonymous filtering result and rollback result. Do not include private connection settings.

## Catalog refresh/deployment procedure (unexecuted)

The runtime reads the checked-in snapshot, not Bandcamp on every visitor request. WordPress's hourly picker refresh is separate: it reads deployed `/api/wordpress/catalog`, never audio and never automatic artist assignment. WordPress scheduled work requires site traffic; manual **Refresh release choices** provides an operator check.

1. Repository operator verifies `bandcamp-sync.yml` is on the actual default branch and Actions are enabled. The workflow currently explicitly checks out/pushes `main`; confirm that is the intended catalog branch. Check `contents: write` is permitted and branch protections/rules allow this bot's commit workflow. Do not broaden token scopes or bypass protection without owner approval.
2. Inspect recent **Sync Bandcamp catalog** runs. Record scheduled start, success/failure, run URL/ID, fetched count, changed/unchanged message and any committed SHA. An hourly cron does not prove timely/successful runs. Investigate failed run logs before retrying.
3. Before a write run, use a temporary checkout/staging environment and `npm run sync:bandcamp:check` if upstream freshness must be compared without changing the checked-in file. A changed snapshot makes check mode exit 1 deliberately; fetch/parser failure also exits 1 with a different log. Tests already cover synthetic no-change/failure fixtures in isolated temporary directories.
4. Obtain refresh/commit/deployment authorization, then dispatch the workflow against the intended branch. Review snapshot diff: sanitized public metadata only. Compare effective archive before/after: stable slugs/catalog codes/editorial fields, explicit relationships, curated entries absent from listing and distinct identities must survive. Never fabricate an upstream change just to force a commit.
5. For changed data, verify successful bot commit/push and record SHA. For unchanged data, verify no new commit and no deploy-hook call. Fetch/parser failure must retain the existing complete snapshot; push races fail the run, and the next fresh checkout can retry.
6. Operator checks whether hosting Git integration actually deploys this bot commit. A GitHub workflow triggered by `push` is not reliable chaining here: pushes made with `GITHUB_TOKEN` do not trigger another push workflow, per [GitHub workflow trigger documentation](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow). Hosting's own integration is a separate system; verify its behavior instead of assuming it.
7. If an approved hook is configured, `BANDCAMP_DEPLOY_HOOK_URL` remains a GitHub secret. Existing code accepts only bounded HTTPS Vercel/Netlify hook endpoints, rejects redirects and uses a 20-second timeout. Log acceptance separately from hosting build completion. No hook setting was read or added during this audit.
8. If hook fails after push, the catalog commit remains remote but the run fails. A later unchanged import skips the hook, so deploy that recorded SHA through the hosting dashboard (with authorization) or use its supported retry procedure. Do not force a metadata change to provoke deployment. If no hook exists, the workflow asks the operator to verify hosting Git deployment; successful sync alone is not release completion.
9. Record hosting deployment ID, built SHA, build completion and public archive/detail/picker content. Refresh WordPress release choices and verify existing editor selections persist. Attach served-content evidence to the workflow/deployment evidence. A browser cache, stale deployment or CMS picker can each differ; diagnose them separately.
10. Recovery: preserve the last good snapshot on import failure; restore the prior known-good commit/deployment through existing operator procedures if the authorized refresh reveals a production regression. Do not delete curated entries or reset user/editor work. Owner chooses who receives Actions/hosting failure notifications and reviews them; no unsolicited messages or recurring monitors were configured.
